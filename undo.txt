## Why the previous entry isn't enough

Your queue is a chronological list of *all* edits, in any order across cells. Suppose:

1. `a1 = 5`
2. `b1 = 7`
3. `a1 = 9`

Undo. The last entry is `a1 = 9`, and the previous entry is `b1 = 7` â€” a different cell entirely. Re-running it does nothing useful; `a1` stays at 9.

To find `a1`'s prior state you'd have to scan backwards through the whole queue looking for the most recent earlier entry with the same name. That works, but it's O(history) per undo, and it fails on the boundary case: if `a1` has never been set before, there's no earlier entry, and the correct undo is *deleting* `a1`, which no entry in the list represents.

`oldInput` records that directly. It's the answer to "what was here before," including the empty case, without searching.

## What undo actually is

The framing that makes this click: an undo entry isn't "an edit," it's **a pair of states for a location.** `{name, oldInput, newInput}`. Undo applies `oldInput`; redo applies `newInput`. Both are just `#setInput` plus `#recalculate` â€” no replay, no scanning, no special sequencing.

Your three-step sequence is trying to reconstruct that pair from the history. The pair is cheaper to record than to recover.

## Two stacks, and the replay flag

```
undoStack: [{name, oldInput, newInput, oldRole, newRole}, ...]
redoStack: []
```

Undo: pop from undoStack, `#setInput(name, oldInput, oldRole)`, `#recalculate([name])`, push the entry to redoStack. Redo: the mirror.

The critical detail â€” and it's the same one that broke your earlier replay â€” is that `#setInput` currently pushes to the queue unconditionally. So undo would record its own undo, and you'd ping-pong forever. Either take a flag, or better: move the queue push *out* of `#setInput` and into `setCellContents`, which is the only entry point that represents a user action. Then `load`, undo, and redo all use `#setInput` directly and record nothing, structurally.

And a new user edit must clear the redo stack. That's standard: once you diverge from the redone future, it's gone.

## Capturing oldInput correctly

Right now `oldInput` is a parameter passed in by Grid â€” which means Grid has to know the previous value, and if it's wrong or omitted, undo silently corrupts. Better for `setCellContents` to read it from the model itself before overwriting:

```js
const old = this.#cells.get(name);
const oldInput = old ? old.input : null;
```

`null` (never existed) is meaningfully different from `""` (was explicitly cleared) â€” undoing to `null` should delete the cell, not store an empty one. Otherwise you leave a phantom record that `#topologicalSort` will happily include.

Then drop `oldInput` from Grid's call entirely. One less thing the view has to get right.

## Two more

**Role changes need entries too.** Marking a row as headers is an undoable action, and it doesn't go through `setCellContents`. Either give it its own entry type or capture role in the same record.

**Fills and deletes span many cells.** One `Ctrl+Z` should undo the whole fill, not one cell of fifty. So an entry needs to be a *list* of cell changes, not a single one â€” undo applies them all, then recalculates once with all names as seeds. That's also why `#recalculate` taking a set of seeds matters.

Given that, `{cells: [{name, oldInput, newInput, oldRole, newRole}], label: "fill"}` is probably the shape to build now rather than retrofit. `label` gives you "undid fill" as an announcement, which is worth a lot when you can't see what changed.

## On range: your first instinct is right, drop it

A range passed alongside the formula creates a cell whose precedents aren't derivable from its own text. That breaks three things at once: saving (the JSON has `input` but not the range, so reload loses the edges), undo (the entry would have to carry it too), and readability (the formula doesn't say what it depends on).

The formula text should be self-contained. `alt+=` already does this correctly by splicing labels into the text before it reaches the model. Anything that needs a range should go the same way.

And it's currently dead anyway — `setCellContents` accepts `range` and passes it to `setInput`, but `#autofill` never passes one, and `endEditing` doesn't either. So removing the parameter costs you nothing today.

## Undo

The three-step sequence you sketched is trying to *recover* the prior state by scanning history. The pair `{oldInput, newInput}` records it, which is why `oldInput` earns its place: with `a1=5, b1=7, a1=9`, the previous queue entry is `b1`, an unrelated cell. And if `a1` had never been set, no earlier entry exists at all — the correct undo is deletion, which no forward entry can express.

You've already got the capture right in `setCellContents`, using `null` to distinguish never-existed from cleared. Good. What's missing is that `undoEntry` is built and then discarded — nothing pushes it. Meanwhile `setInput` still pushes to `#replayQueue`, which means `load`, undo, and redo would all record themselves. Move the push up into `setCellContents` and delete it from `setInput`; that's what makes recording structurally impossible on the replay paths.

Then undo is: pop, `setInput(name, oldInput, oldRole)` for each cell in the entry, `recalculate` with all their names, push to a redo stack. A new user edit clears redo.

Since `#autofill` and `delete` both touch many cells, build the entry as `{cells: [...], label: "fill"}` now rather than retrofitting — and `label` gives you "undid fill of 12 cells" as an announcement.

## Bugs in the code you sent

**`#autofill` shadows and misuses `label`.** `for (label of range)` assigns to the parameter — and in a module that's a `ReferenceError` since `label` is a `const` binding from destructuring... actually it's a parameter, so it just silently clobbers. Either way, the last loop is worse:

```js
for (label of range) this.#renderCells([...range]);
```

That renders the entire range once per cell — n² renders. It should be a single `this.#renderCells(...)` on the result of `recalculate`, which is the authoritative changed set (the fill's dependents may be outside the range).

**`#autofill` ignores `#fillFormula`.** It writes the same literal text into every cell, so filling a formula gives you identical formulas rather than relative ones. Presumably not yet wired up.

**`#evaluate`'s precedent-error branch returns without setting `cell.value`.** So a cell whose precedent has an error keeps its previous value and looks fine. The `console.log` even prints `cell.value` before it's assigned. You need `cell.value = <the propagated error>` before returning — and propagating the *original* error is more useful than a generic one.

**`recalculate`'s `skipDirtyComputation` is inverted in effect.** When true you use `names` as-is; `load` passes all names so that's right. But `#autofill` calls `recalculate([...range])` with the default, which does compute the dirty set — correct. Just note the flag name says "skip" while the common case is "don't skip"; `expandDirty = true` reads better.

**`parseLabel` contract, again.** `setInput` does `if (result.error)` while `evaluateRefs` and `#evaluate` do `[row, column] = parseLabel(...)`. Those can't both be right.

**`initialScope` returns 0-based row/col** (whatever `parseLabel` gives), so in `a1`, `_row` is 0. Then `toLabel(...)` in `evaluateRefs` presumably expects the same basis — consistent internally, but `ref(1,0)` meaning row 2 will confuse you later. Worth settling on 1-based for anything user-facing.

**`_r`/`_c` and `_row`/`_col` are four names for two values.** Fine, but they're also four names `getSymbols` must exclude, and the exclusion list needs to match `initialScope` exactly or you get phantom precedents.

## Turn it around

The problem is that `setCellContents` is both "change one cell" *and* "record one undo entry." Those are welded together, so any operation touching many cells either gets many entries or needs to tell the model it's special.

Split them:

- `setInput(name, input, role)` — change one cell. Records nothing.
- `recalculate(names)` — evaluate. Records nothing.
- `pushUndo(entry)` — record one undoable action.

Now the controller composes them. A single edit does one `setInput`, one `recalculate`, one `pushUndo` with one cell in it. A fill does fifty `setInput`s, one `recalculate`, one `pushUndo` with fifty cells in it.

Same primitives, different composition. Nothing tells the model what kind of operation is happening, because the model doesn't need to know — the *shape of the entry* carries that, and the caller builds it.

`setCellContents` then becomes a convenience wrapper for the single-cell case, which is what it already effectively is.

## Where the old values come from

The one thing the controller can't easily do is capture `oldInput` — it would have to ask the model for each cell's current state before overwriting.

Simplest fix: have `setInput` *return* the old input and role alongside the cell. Then the controller accumulates them as it goes:

```js
const changes = [];
for (const label of range) {
  changes.push(this.#model.setInput(label, text, role));
}
this.#model.pushUndo({cells: changes, label: "fill"});
this.#renderCells(this.#model.recalculate([...range]));
```

`setInput` gives back what it replaced; the controller decides what constitutes one undoable action.

## The nagging question

Where should the undo stack live — model or controller? Both are defensible.

In the **model** it survives naturally alongside `#cells`, and undo can call `setInput` directly. But then the model owns something that's arguably a UI concept.

In the **controller** it's clearly a session concept, and it can hold non-model actions too. Which matters more than it sounds: marking a row as headers, and possibly cursor position restoration, aren't cell edits. If undo lives in the model, those either can't be undone or need a parallel mechanism.

I'd put it in the controller for that reason. The model exposes `setInput` and `recalculate` and stays a pure calculation engine; the controller owns "what the user did."

## The thing that makes undo feel right

Restore the cursor and the mark. Undoing a fill should put you back where the fill started, not leave you wherever you happened to wander. Store the cursor position in the entry and have the controller restore it — trivial to add now, and without it undo is disorienting since nothing tells you what changed or where.

And your instinct was actually sound: you checked that `c.redo` existed and was a function before suspecting the keymap wiring. It was. The problem was that identity and behaviour had come apart, which isn't something a reasonable first hypothesis covers.
